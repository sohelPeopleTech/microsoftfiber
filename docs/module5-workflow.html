Where the alert sits, and what happens after someone reads it

The analysis is built and running. This is the operating workflow around it — who receives a finding, what they do with it, what the system does in response, and how the loop closes.

1 · The operating loop

Solid boxes exist and run today. Dashed boxes are the workflow around them — the part that turns an alert into an action with an owner and an outcome.

built and running to build
The gap, stated plainly

Today a finding is read. Nothing records that it was read, nobody is assigned, and next Monday the same finding is posted again with a slightly larger number — because unfulfilled tickets keep accruing. Without the dashed half, the alert repeats rather than resolves.

2 · What Approve and Reject actually do

This is the decision that unblocks everything else, and it is not ours to make alone. Approve cannot mean "raise the threshold automatically" — that is a capacity policy change requiring authority the agent does not have, and the design explicitly forbids auto-execution.

OptionOn ApproveNeedsEffort
A · Acknowledge Log who approved and when; @mention the region owner in-thread; suppress the repeat for N cycles Nothing beyond TeamsSmall
B · Raise a work item (recommended) Create an ADO / ICM item with the region, the sized threshold, the evidence incidents and a due date; link it back into the thread ADO or ICM project + service accountMedium
C · Draft the change Generate the actual capacity-policy change request, routed for a second approval before submission Access to the capacity-request systemLarge

B is what "the capacity team who's working on it" implies — Approve should put something in someone's queue, with the sizing and evidence already attached, so the work does not have to be re-derived from the message.

Reject is not a dead end

A rejection carries a reason, and the reason is a signal worth keeping:

  • "Threshold is already being raised" → suppress this region until the next quarter
  • "That customer is churning" → exclude the subscription from exposure
  • "48h is the wrong cut-off for Standard tier" → change the SLA in config, which re-scores every ticket

Recorded rejections are how the alert stops crying wolf. Without them it repeats the same finding indefinitely.

4 · Keeping the alert true when things change

His question — "if thresholds get increased or cores get increased, is my alert calling out the same thing?" — is the sharpest one asked, and today the answer is no.

What changesTodayShould be
New tickets arrive in ICMPicked up next Monday Trigger a run on arrival
A threshold is actually raisedNot detected — the same finding reappears Detected; the finding closes and the loop reports the drop in exposure
The SLA cut-off is changedNeeds a config edit and a manual re-run Config change re-scores every ticket automatically
An unfulfilled ticket is finally grantedSilently stops accruing Reported as resolved, with the final cost of the delay
Per-tier SLA — a change to the model

He described different cut-offs per subscription tier — 48h for Enterprise, 24h or 32h for others. Today there is a single global 48-hour cut-off applied to everyone. Making it per-tier changes which tickets count as failures, and therefore every number in the report. This needs the real SLA table before it can be implemented.

5 · What we need decided

Decision 1

What does Approve produce?

Acknowledge in-thread (A), raise a work item (B), or draft the policy change (C). If B, which system — ADO or ICM — and which project.

Decision 2

What is the SLA per subscription tier?

Enterprise 48h was mentioned, with 24h and 32h for others. The real table changes what counts as a failure and every figure downstream.

Decision 3

Who owns each region?

The card should name an owner. A region-to-team mapping does not exist yet — without it, "Owner" stays generic and nobody is actually accountable for a finding.

Decision 4

Should the agent answer questions in the channel?

The engine is built — ranking, totals, per-customer, per-incident, methodology, all answered from the same computed tables. Making it two-way needs a registered Teams bot rather than the current one-way webhook. That is an integration and an app registration, not new analysis.
